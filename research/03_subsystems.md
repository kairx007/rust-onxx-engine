# 03 — Subsystem deep dives

Legend: **[PRESENT]** implemented in this repo · **[DELEGATED]** done by ONNX Runtime, not by this code · **[ABSENT]** not in the repo (the brief listed it, but it doesn't apply to this project). Every [ABSENT] claim is backed by the grep in `00_inventory.md` header.

## 1. Model formats and supported architectures
- **[PRESENT] ONNX only.** README/`docs/running-a-model.md#1-confirm-the-model-format-and-contract`: `.pt/.pth/.h5/.keras` are not loaded. **No GGUF, no safetensors.** Loader: `Session::builder(env).commit_from_file(path)` (`src/runtime/session.rs:47-48`); file existence pre-check `:40`.
- **Architectures:** two, identified by the `ModelType` enum (`src/models/registry.rs:10-16`): `DeepLob`, `TransformerLob`. The Rust code does not know their internal structure; it knows only an I/O contract. (Architecture claims — DeepLOB CNN+LSTM ≈66K params, TransformerLOB CNN+2-layer/4-head Transformer ≈114K — come from `llm_context/context.md` §4 and the IEEE PDF; [TODO: dump op types from the two `.onnx` files to confirm].) No LLaMA/Mistral/etc.
- **Contract validation (non-trivial part):**
  - Generic: exactly 1 input & 1 output, both `Float32`, input rank 4 and each *static* dim equal to `[1,1,100,40]`, `-1` (dynamic) accepted; output final dim = 3 when static (`src/runtime/metadata.rs:44-103`, `validate_dimensions :106-133`).
  - DeepLOB: additionally output prefix dims must be `1` or dynamic (`src/models/deeplob.rs:73-101`).
  - TransformerLOB: input rank/axes checked against the config; output prefix dims `!= 1 && >= 0` rejected (`src/models/transformerlob.rs:76-139`). The two contracts are near-duplicates (≈same logic written twice) → maintainability remark, not novelty.
  - Tensor names are *discovered*, not hard-coded (`deeplob.rs:48-53`; tests use names like `actual_input`, `:128-139`).
- **Observed models** (my `inspect` runs, 2026-11-22): both inputs `input` `[-1,1,100,40]` Float32; DeepLOB output `output` `[-1,3]`; TransformerLOB output `output` `[1,3]`. So the models are *dynamic-batch on input* even though the proposal PDF says "fixed input shape [1,1,100,40]" (M-8), and the engine only ever sends batch = 1.
- `transformerlob.onnx` uses ONNX *external data* (`transformer.onnx.data`), loaded implicitly by ORT relative to the model path. Not documented anywhere in the repo (M-9).

## 2. Tensor representation and memory layout; mmap / zero-copy
- **Representation:** a plain owned `Vec<f32>` + `[usize;4]` shape (`src/tensor/input.rs:9-13`). No `ndarray` in project code (the `ort` `ndarray` feature is not requested, `Cargo.toml:16`; ndarray is only a transitive lock entry). Layout is row-major NCHW with N=C=1: flat index `t*40 + f` (time-major rows of 40 features) — verified by tests asserting `data[40] == 40.0` (`src/inference/input.rs:81`).
- **Dataset layout:** per segment `features: Vec<f32>` (rows×40 contiguous) and `labels: Vec<u8>` (`src/data/dataset.rs:13-17`), invariant-checked on construction: length, finiteness, label ∈ 0..=2 (`:20-65`).
- **Copies on the request path:**
  1. CSV text → `f32` (`feature_extractor.rs:20`).
  2. In-place normalization (no copy, `normalization.rs:147-165`).
  3. **One copy per window**: `segment.features()[start..end].to_vec()` (`tensor/input.rs:39`), 16,000 bytes.
  4. Borrowed hand-off to ORT: `TensorRef::from_array_view` (`inference/input.rs:9,39`). The docs call this "borrowed `TensorRef<f32>` … without cloning its feature buffer" (`phase-03` doc, HEAD). **Evidence-level caveat:** whether ORT copies internally on CPU is inside ORT; I did not verify. [TODO: confirm via ORT docs/source that CPU `TensorRef` from a slice is zero-copy.]
  - `InputTensor::into_ort_tensor` (owned, `Vec → Box<[f32]>`, `tensor/input.rs:59-68`) exists but is **not used on the inference path**: `grep -rn into_ort_tensor src tests examples` finds only its definition and `tests/tensor_tests.rs:69` (a public-API method kept for the Phase-2 spec; the real path is the borrowed view).
  - A cheaper design (borrow a window slice of the segment buffer directly, skip `to_vec`) is possible because windows are contiguous; the code does not do it. This is an *optimization opportunity*, not a contribution.
- **mmap:** **[ABSENT]** (no `memmap2`; `std::fs::File`/`BufReader` only). Model-file loading is entirely ORT's (`commit_from_file`); whether ORT mmaps is [UNCLEAR/DELEGATED].

## 3. Kernels: matmul, SIMD, GPU backends, threading
- **[ABSENT in this repo / DELEGATED to ORT].** No matmul, no SIMD intrinsics, no `std::arch`, no GPU. The CPU execution provider is selected explicitly (`ep::CPU::default().build()`, `src/runtime/environment.rs:32`). Any other provider string is rejected (`:26-28`; tests `tests/runtime_tests.rs:15`, `tests/config_tests.rs:39`). Error text is stale: "Phase 1 supports only 'cpu'" (`src/error.rs:23`).
- **Threading model:** the Rust side is single-threaded. `run_prediction` is a sequential `for` loop over windows (`inference_service.rs:94-98`); the engine requires `&mut self` (`engine.rs:35`; `ModelSession::session_mut`, `session.rs:84`), so one session cannot serve concurrent requests without external locking. ORT's intra/inter-op thread pools are left at defaults — **never configured** (grep for `intra|inter_op|with_*threads|optimization_level` in `src/` → no hits). The only extra thread is the optional `ResourceSampler` (`benchmark/resources.rs:37`) which spawns `ps` every 100 ms.
- **Graph optimization level, memory arena, etc.:** not set → ORT defaults [UNCLEAR what the defaults are in this `ort` rc.15; TODO: log/print them].

## 4. Quantization formats and dequantization
- **[ABSENT].** All tensors f32 end to end (`INPUT_SHAPE`/dtype guards: `tensor/validation.rs`, `settings.rs:260`, `metadata.rs:54,64` require `Float32`). Whether the `.onnx` files internally contain quantized ops is not examined → [TODO].

## 5. Attention implementation (naive / flash / GQA / RoPE)
- **[ABSENT / DELEGATED].** TransformerLOB's attention lives inside `transformerlob.onnx`; Rust never touches it. No RoPE/GQA/flash concepts apply. The only "attention"-related text in the repo is the model name and docs.

## 6. KV cache
- **[ABSENT].** The models are stateless single-shot classifiers over a fixed 100-step window; no autoregression, so no cache, growth, reuse, or eviction. Each call is independent; windows do not overlap (stride = 100) so there is also no sliding-window state reuse (`window.rs:14`).

## 7. Batching, streaming, sampling
- **Batching: [ABSENT].** Strictly batch = 1. Enforced in three places: config (`settings.rs:178`), tensor (`validation.rs:3-10`), output parser requiring all prefix dims `== 1` (`inference/output.rs:33-41`). The models accept `-1` batch (observed), so batching is a *model-side capability the engine deliberately forbids*. The C++ paper projects "B = 32 … below 0.2 ms" amortized as future work (IEEE PDF §VIII.B; unmeasured there too).
- **Streaming:** only output-file streaming: rows serialized one at a time to a temp file; atomic publish; `Drop` cleanup (`output_writer.rs:66-168`). Atomicity detail worth noting: no-overwrite mode publishes via `hard_link` + `remove_file` so a concurrent creator of the destination yields `AlreadyExists` → `OutputExists` rather than a clobber (`:142-151`); overwrite mode uses `rename` (`:135`). `sync_all` before publish (`:128`). Tests: `output_writer.rs` has 4.
- **Sampling:** [ABSENT]. Decoding rule is greedy argmax with deterministic lowest-index ties (`prediction.rs:46-54`), `total_cmp` so NaN would be totally ordered, but non-finite scores are rejected first (`:40-45`). Scores are **returned as the model emits them** (no softmax; docs: "unknown whether logits or probabilities"). Observed outputs include negative values, e.g. DeepLOB smoke test `Down=-0.49 Stationary=1.92 Up=-1.85` (my run) → they are logits; TransformerLOB smoke test scores were all near 0 (`-0.072, 0.0058, -0.096`) [UNCLEAR whether untrained/degenerate on zero input].
- **Label mapping:** FI-2010 1/2/3 → internal 0/1/2 = Down/Stationary/Up (`labels.rs:5-26`). The label accepted as `f64` so `"1.0"` works (commit `2422326`).

## 8. Rust-specific engineering
- **`unsafe`: 0 occurrences.** `#![forbid(unsafe_code)]` at crate level (`src/lib.rs:2`) *and* `unsafe_code = "forbid"` in the manifest (`Cargo.toml:30-31`); `grep -rn unsafe src tests examples build.rs` → only that attribute line. All FFI `unsafe` is inside `ort`/`ort-sys`, outside this crate's audit boundary. Consequence for the paper: "memory-safe wrapper" is a true property of *this crate's code*, not of the whole binary.
- **Ownership/lifetimes:** one non-trivial lifetime use — `adapt<'a>(&'a InputTensor) -> TensorRef<'a,f32>` ties the ORT input view to the tensor's buffer (`inference/input.rs:5,13-16`), so the borrow checker prevents use-after-free of the input during `run`. `Session::run` needs `&mut Session`, forcing `&mut self` through `ModelSession → Engine → LoadedModel` (`session.rs:84`, `engine.rs:35`, `model_factory.rs:19`).
- **Traits/generics for backends:** **none.** Backends are not abstracted: `LoadedModel` is a closed `enum { DeepLob(..), TransformerLob(..) }` with a `match` (`model_factory.rs:13-25`); the two engines share `runner::predict` (`runner.rs:11`) but no trait. There is no `Backend` trait, so "pluggable backends" cannot be claimed.
- **Global state:** `static ENVIRONMENT: OnceLock<Result<Environment,String>>` (`environment.rs:8`) — process-wide ORT environment, init failure is cached as a `String` (losing the typed error). `static NEXT_TEMP_ID: AtomicUsize` for temp filenames (`output_writer.rs:11`).
- **Error handling:** library returns a single typed `AppError` (`thiserror`, 42 variants incl. path/row/column context, `src/error.rs:7-167`); `anyhow` only in `cli/commands.rs`. Non-test `unwrap/expect`: **17**, all in orchestration/bench code (`inference_service.rs` 8, `benchmark/comparison.rs` 6, `cli/commands.rs` 2, `benchmark/resources.rs` 1) and all on invariants established a few lines earlier (e.g. `.expect("inference mode prepares input")`); **zero** in `inference/`, `runtime/`, `tensor/`, `models/`, `data/`, `preprocessing/`.
- **Allocations on the hot path** (per window, `predict`): `to_vec` 16 KB (`tensor/input.rs:39`); two O(4000) finite-scans (`validation.rs:18-26`, executed in `from_window` and again in `adapt`); `ort::inputs![]` + `SessionOutputs` allocated by ORT/ort; a 3-float `Prediction` by value; in `predict` mode a `PredictionRow` with `source_file: String` allocated *per row* (`output_writer.rs:44`). No pooling/reuse of the tensor buffer. [TODO Phase 2: allocation count per call, e.g. with `dhat`/counting allocator — the proposal lists "allocation count" as a metric but nothing measures it.]
- **Validation-first design (the project's real "novelty" if any):** nearly every boundary has a typed, positional error: CSV row/column, label, finite checks, NPY shape/order, schema gate, output shape, window reference; plus `deny_unknown_fields` config. It is engineering rigor rather than algorithmic novelty.
- **Hard-coded vs configurable:** `100`/`40`/`3` are duplicated as literals in `tensor/validation.rs:3-4`, `tensor/input.rs:19`, `window.rs:14`, `inference/output.rs:33`, `data/dataset.rs:5`, `feature_extractor.rs:11-12`, `settings.rs:178-260`, even though `ModelSpecs` is "configurable". Changing the window length means touching ≥8 places.

## 9. Testing, correctness checks, benchmarks
- **Counts:** `cargo test --offline` (run 2026-11-22): **27 lib unit tests + 36 integration tests = 63 passed**, 0 doc tests. Integration files: `config`(9) `csv_loader`(7) `normalization`(4) `tensor`(3) `window`(3) `model_loading`(3) `feature_extraction`(2) `label`(2) `runtime`(2) `pipeline`(1). Prior docs' counts (13/36/43/46/59) are cumulative snapshots per phase (M-4).
- **What is tested:** synthetic CSVs, NPY stats, windowing, tensor layout, metadata contracts (with fabricated `ModelMetadata`), output parsing, writer atomicity, report round-trip, CLI parsing. `tests/model_loading_tests.rs` rejects an invalid ONNX file.
- **What is NOT tested:** no test loads `models/deeplob.onnx` / `transformerlob.onnx` and compares outputs to a reference; **no numerical-equivalence test vs PyTorch or C++** (spec target abs tol 1e-5, `llm_context/context.md` Phase 7); no property/fuzz tests; no test of real FI-2010 data (the files are absent). Docs say this explicitly (`running-a-model.md#11`).
- **Existing benchmarks:** in-binary harness only (`benchmark/`), no `cargo bench`/Criterion. Harness properties: wall-clock `Instant` per call (`inference_service.rs:200-202`); warm-up default 20, 200 iterations × 5 trials; nearest-rank percentiles (`statistics.rs:47-50`) and population std (`:29-33`); **same tensor reused every call** (`:191`); throughput = completed / sum of trial wall times; JSON keeps every sample (`report.rs:15-24`); metadata includes FNV-1a model fingerprint (`inference_service.rs:462-478` — non-cryptographic), git short hash, rustc version, OS/arch, CPU brand (via `sysctl`/`/proc/cpuinfo`), RAM. Weaknesses to fix before claims: `runtime_version` is a **literal string** (`:373`), not queried from ORT; thread config is a literal (`:384`); no CPU-frequency/thermal/background-load capture; no pinning; trials run back-to-back in one process (no process isolation, which the proposal §7.7 requires); resource sampler uses `ps` subprocesses (perturbs the run); the `compare` command *requires* `model_file_hash` equality (`comparison.rs:40-41`) but the C++ side must emit the same FNV-1a field in the same JSON schema — no C++ code exists here to do so.
- **Example data on disk:** see `04_paper_evidence.md` §2 — the single real report shows heavy variance (mean 7.80 ms vs median 2.14 ms).
